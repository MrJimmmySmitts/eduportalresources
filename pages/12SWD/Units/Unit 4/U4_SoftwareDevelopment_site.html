SAT Transition & Outcome 1 Overview
Orientation

Your School-assessed Task (SAT) does not restart in Unit 4 — it continues. Unit 3 Outcome 2 (Criteria 1–5) is complete. Unit 4 Outcome 1 (Criteria 6–10) is the next stage of the same piece of work, assessed against the same rubric.

Unit 4 Outcome 1 — official outcome statement
Develop and evaluate a software solution that meets requirements and assess the effectiveness of the project plan.

What the finished Outcome 1 body of work contains

  • A software solution that meets your software requirements specification (SRS)
  • Preparation and conduct of beta testing
  • An evaluation of the efficiency and effectiveness of the software solution
  • An assessment of the effectiveness of the project plan (Gantt chart) in monitoring project progress

The last two items are presented as one of: a written report, or an annotated visual plan. Time allocated for Outcome 1 is at least 8 weeks of class time — that's Weeks 1–8 of this term.

Important boundary — read carefully If your Unit 3 design has issues that will affect development, your teacher can give feedback on the quality of the design — but any changes to the design must be your decision, not something your teacher directs. Changing your design does not get your Unit 3 score reassessed; your original Criteria 1–5 scores stand either way.
How this actually gets submitted Your finished software is delivered as a compressed (zipped) folder containing everything needed for it to run — negotiate the exact delivery format with your teacher. The evaluation and project-plan documents are not essays — use headings and dot points, the same way a professional report would.

Development Environment & Repository Setup
Orientation

A tidy, version-controlled workspace is what turns your pseudocode modules into working code without losing your place. Set this up properly once, now, and it pays off for the next eight weeks.

What to set up today

ComponentPurpose
IDE / editorWhatever programming language and environment you specified in your Unit 3 design and technical environment section.
Code repositoryVersion control (e.g. Git) — every saved milestone is a discrete, meaningful commit, not "final_final_v3". A repository also gives you a full history to fall back on if something breaks.
Folder / module structureOne clearly named location per module, matching the module names in your design — not ad hoc file names invented while coding.
BackupA second location (external drive, network drive or secure cloud storage) — required for authentication purposes.
Why version control, specifically A repository isn't just backup — it's a record of every working state your solution has been in. If a change breaks something, you can see exactly what changed and roll it back, instead of guessing. Commit only working, tested code where possible — resist the temptation to commit something "temporary" and forget to fix it.
Build order Use your design readiness check from Lesson 2 to decide which module to build first — usually the one with the fewest dependencies on the others, so you have something working early.

Week 1 · AoS1
Programming Language Features I
Criterion 6

Variables, constants, data types, and the two simplest control structures — sequence and selection — are the foundation every other language feature in this unit builds on.

Data types and structures — input, storage, output

Every data type or structure behaves differently at three points: how it's input, how it's stored, and how it's output. Knowing all three matters more than just knowing the type's name.

Data type / structureTypical inputOutput consideration
CharacterSingle symbol via keyboardDisplayed as a visual symbol
StringSequence of symbols via user input or fileDisplayed in original character order
IntegerWhole number, decimal representationDisplayed as a whole number
Floating pointDecimal input with a fractional partDisplayed to a set precision
Date/timeString input or a UI date pickerFormatted per your solution's date/time convention
One-dimensional arraySequential or indexed entriesDisplayed as an ordered list
Two-dimensional arrayEntered by row and columnDisplayed as a table/grid
RecordMultiple related fields entered togetherDisplayed as a grouped set of fields
Check against your data dictionary Your Unit 3 data dictionary should already specify which of these each data item uses. Today you're translating that specification into real declarations — not choosing types freely.

Local, global and constant — by scope, not by convenience

Variable typeScopeWhen to use it
Local variableDeclared and only accessible within a single function/moduleDefault choice — use unless something outside genuinely needs it
Global variableDeclared outside any function — accessible everywhereOnly when multiple modules genuinely need to read or change the same value
ConstantFixed value that cannot change once set, conventionally uppercaseAny value that shouldn't change during execution (e.g. a maximum size, a tax rate)

Sequence and selection

Sequence is the default: instructions run in the exact order they're written. Selection is branching logic that directs the flow depending on a condition — and it comes in two shapes:

  • Binary branching — a single If/Then (with an optional Else) choosing between two paths.
  • Multiple branching — a Switch/Case (or If…Then…Else chain) choosing between several possible paths.
Stacking vs nesting Control structures combine in only two ways: stacking (one after another, in sequence) or nesting (one placed inside another). Know which one your pseudocode actually calls for — they behave very differently.
Common mistake Defaulting to global variables because they're "easier" — a global used where a local one belongs is exactly the kind of choice Criterion 6's higher bands expect you to have moved past.

Week 2 · AoS1
Programming Language Features II
Criterion 6

With sequence and selection working, today adds the third control structure — iteration — plus the operators that make conditions and calculations possible.

Iteration — three shapes, same job

Iteration (repetition) repeats a block of code. Which shape you choose depends on when the loop's condition is checked, and whether you know the number of repetitions in advance.

Loop typeWhen the condition is checkedUse it when…
Pre-test (e.g. While…Do)Before the loop body runs — may not execute at allThe loop might legitimately need to run zero times
Post-test (e.g. Do…While, Repeat…Until)After the loop body runs — always executes at least onceThe loop must run at least once regardless of the condition
Counted (e.g. For…Next)Tracked against a counterYou know exactly how many repetitions are needed in advance
Watch for infinite loops If a pre-test or post-test loop's condition can never become false, it never ends. Always check: does something inside the loop actually move the condition toward becoming false?

Operators

TypeExamplesUsed for
Arithmetic+ − × ÷ (and modulus, remainder after division)Calculations on numeric data
LogicalAND, OR, NOTCombining or inverting multiple conditions
ConditionalComparison operators inside an If/Switch conditionDeciding which branch of a selection structure runs
Combining operators with iteration A counted loop's exit condition is itself a conditional operator comparing the counter to a target value. A logical AND/OR often combines two conditions inside a single loop or selection test — check your pseudocode for exactly where these appear.

Week 2 · AoS1
Programming Language Features III
Criterion 6

Today shifts from top-down flow to event-driven flow — the model behind every graphical user interface — plus the difference between a function and a method. Work on your second module begins.

Graphical user interfaces are event-driven

Everything so far — sequence, selection, iteration — has run in an order you control. A GUI flips that: the program waits, and the user's actions (a click, a keypress, a menu selection) decide what runs next and when.

What this means for your build Each interactive element on your GUI (a button, a field, a menu item) needs its own event handler — a block of code that runs only when that specific event happens. You're not writing one long script anymore; you're writing many small responses to possible user actions.

Functions vs methods

TermWhat it is
FunctionA standalone, reusable block of code — takes input (parameters), does something, optionally returns a result. Not tied to any object.
MethodA function that belongs to an object or class — it can access and change that object's own data.
Why the distinction matters If your solution uses classes and objects (even simple ones), code that only makes sense in relation to a specific object's data should be a method on that object — not a free-floating function that has to be passed the object's data every time.

GUI reminder

Criterion 6 expects GUIs genuinely demonstrated across your solution — check your own design for which modules need one. If your second module is one of them, its event handlers are today's main build target.

Working code isn't the same as good code. From today, Criterion 7 assesses how your solution communicates itself — to a marker, and to you in six weeks' time.

Validation Techniques
Criterion 7

Validation checks that input data is reasonable — it can't tell whether someone is lying, but it can catch nonsense before it breaks your solution.

CheckWhat it catches
ExistenceA required field was left blank or null.
TypeData isn't the right kind — e.g. letters entered where a number was expected.
RangeData is outside an acceptable range — e.g. an age of 174.
Validation ≠ verification Verification checks that you're building the thing correctly against your requirements. Validation checks that the finished thing actually behaves sensibly when real data hits it. You need both, but they're not the same activity.

Debugging & Alpha Testing I
Criterion 8

Alpha testing is internal — you and your development team, in your own environment, checking the solution meets its initial requirements before anyone outside sees it.

The debugging process

  1. Set breakpoints at critical points in the code
  2. Run the program and observe its behaviour
  3. When it hits a breakpoint, it pauses — inspect variables and data
  4. If needed, comment out sections suspected to be problematic, to isolate the issue
  5. Modify the code to fix what you've identified
  6. Repeat until it functions correctly
Commenting out ≠ deleting Temporarily disabling a section of code (rather than deleting it) lets you test the rest of the program in isolation without losing your work if the section turns out to be fine after all.

Beta Testing
Criterion 9

Beta testing is where a nearly-complete version of your solution meets real end users, on their own equipment, in real-world conditions — not yours.

Compressed lesson — plan for time outside class This lesson covers strategy AND conduct together. Recruiting users and running your beta test needs to happen largely outside this lesson — start recruiting today, don't wait.

What your beta testing plan needs

  • Test scenarios targeting your solution's functional and non-functional requirements
  • At least two potential users recruited and scheduled — chosen and justified (not just "whoever was free")
  • A method for collecting results as they happen — not just a memory of how it went
Collecting results Screen recording, live observation notes, or direct feedback forms all work. Whatever you choose, record technical issues, usability issues and user feedback as they occur, not reconstructed afterward.

Week 6 · AoS2
Organisations, Development Models & Vulnerabilities
Outcome 2

Outcome 2 starts here — a shift from building your own solution to analysing how organisations develop software securely (or don't).

In-house vs external development

In-houseExternal
ControlHigh — direct oversight of the whole processLower — dependent on the external provider's practices
CostHigher ongoing staffing costOften lower upfront, but less predictable long-term
ExpertiseLimited to what the organisation already hasAccess to specialised skills the organisation may lack

Vulnerabilities in insecure development environments

Common sources of risk during development itself (not just the finished product): APIs exposing insufficiently secured endpoints, malware, unpatched software, poor identity and access management, man-in-the-middle attacks, insider threats, undisclosed security incidents, third-party software risk, ineffective code review, and combined development/testing/production environments where insecure code can reach live data.

Why "combined environments" matters Keeping development, testing and production separate isn't bureaucracy — it stops untested code from ever touching real user data, and makes it far easier to trace where an issue actually came from.

Evaluation of Solution & Project Plan
Criterion 10

Evaluation is not testing — testing checks the solution works; evaluation checks how well it satisfies the need it was built for, using the criteria you set back in Unit 3.

Compressed lesson — three components in one Today covers solution evaluation, proposing a future evaluation strategy, and assessing your project plan's effectiveness. Come with your beta test results and your full Gantt chart history ready.

Evaluating the solution

For each of your Unit 3 evaluation criteria, choose an evaluation method: objective (measurable, fact-based) wherever possible, or subjective (interviews, surveys, opinions) where a measurable fact isn't available. Consider efficiency (resource use, functionality, speed of processing) as well as effectiveness (does it meet functional and non-functional requirements).

Proposing a future evaluation strategy

Because you won't have long-term user data, propose how the solution should be evaluated later: a timeframe, which criteria to use, and who would be responsible for conducting it.

Week 7 · AoS2
Security Controls, Threat Modelling, Legislation & Ethics
Outcome 2
Compressed lesson — the widest-content session in the unit Four areas in one lesson. This is dense — lean hard on L18's SAC revision to consolidate what doesn't stick today.

Security controls

Version control/code repositories, identity and access management, encryption, code review, patching, and separated development/testing/production environments.

Threat modelling — the process

  1. Determine threats — identify what could go wrong (unauthorised access, data breaches, malware, denial-of-service)
  2. React to threats — develop specific security requirements in response
  3. Prioritise — not all requirements can be implemented at once; rank by potential impact
  4. Confirm mitigation — verify the control actually addresses the threat

Key legislation

Law / frameworkCovers
Copyright Act 1968Protects creators' rights over creative and artistic works
Essential Eight (ACSC)Industry framework of mitigation strategies, assessed across four maturity levels
Information Security ManualAdditional security mitigation guidance
Privacy Act 1988 (APPs)Governs how personal information can be used federally
Privacy and Data Protection Act 2014 (IPPs)Victorian equivalent, governing information privacy

Ethics

Legal and ethical are not the same thing — something can be legal and still widely regarded as wrong. Consider: bias in AI-driven decision-making, intellectual property conflicts, and the consequences of ineffective security practices even where no law was technically broken.

General Exam Revision II
Exam prep

The last Software Development lesson before trial exams. Today is targeted — working directly on the gaps identified in L20, not a general re-read of everything.

Exam technique

  • Read the command term first, then the question — it changes what kind of answer is expected.
  • Match your answer length to the marks available — a 1-mark question doesn't need a paragraph.
  • For case-study questions, refer explicitly back to the case study — generic answers lose marks even when correct in principle.
Before you leave today Everyone should be able to name their top 3 remaining weak spots and have a specific plan for addressing each one before trial exams — not just "I'll study more."
