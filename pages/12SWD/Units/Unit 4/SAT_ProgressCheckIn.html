SAT Progress Check-In

A working checkpoint for your Software Development Practices Log — record your solution's module breakdown, build order, and how your functional requirements are turning into working code. This is a formative tool, not a scored SAT criterion — use it to keep your project plan honest.

1
Solution Design

Module Breakdown

Application

List the modules your solution is actually being built from. There's no fixed number of modules expected — use however many genuinely reflect how you've divided the problem. For each one, describe what it does and how far along it is.

Before you fill this in: look back at your detailed design (Criterion 5) — object descriptions, IPO charts, pseudocode modules. This table should match what you actually designed, not what you think sounds impressive.

Solution Design

Build Order

Application

Sequence the modules above into the order you'll actually build and test them in. Think about which modules other modules can't function without — that dependency is what should drive your order, not what feels easiest to start with.

Your build order here should be consistent with the sequencing and critical path in your Gantt chart (Criterion 1). If they don't match, one of them is wrong — fix it now rather than at Criterion 10.

Development

Functional Requirements → Code

Application

Pick up each functional requirement from your SRS (Criterion 3) one at a time and track how your approach to coding it has iterated. This is where you show your thinking changed as you tested and debugged — not just a final answer.

🟢 Foundation — track 2–3 core requirements 🟡 Developing — track most of your requirements 🟣 Extending — include a requirement where your approach changed significantly, and explain what the earlier version got wrong
