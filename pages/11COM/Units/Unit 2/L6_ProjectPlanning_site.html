Explicit Explanation · D4.2 Why Project Plans Matter

A good idea and a good specification don't automatically turn into a finished solution — a group also needs a shared plan for who is doing what, when, and in what order. Without one, groups typically discover coordination problems only when it's too late to fix them.

Three checkpoints across your project

Your project has three group milestones built in: this one (problem statement + project plan), a preferred design milestone, and a build-substantially-complete milestone before testing begins. Each one exists so that a group's coordination gets checked before moving into a phase that depends on the previous one being genuinely finished.

Today you'll turn last lesson's specification into a task list, sequence it into a Gantt chart, and make sure every task has a named owner — the plan your group will actually work from for the rest of the project.

2
Explicit Explanation · D4.2 From Specification to Task List

Your functional requirements from Lesson 5 describe what the solution must do. A task list breaks the work of building it into discrete, assignable pieces — including work that isn't a functional requirement itself, like testing, documentation, and design.

Too vague to schedule

"Build the app."

Schedulable task

"Build the check-in notification screen and connect it to the reminder trigger."

Don't forget the non-building tasks

A realistic task list usually includes more than just "build feature X" items — for example: finalising the design, sourcing or learning a new tool, building each major feature, integrating features together, user testing, expert review, and preparing the final submission.

3
Explicit Explanation · D4.2 Estimating Time Allocation

Because your doubles run on a fixed fortnightly rhythm for the rest of the term, the most useful unit for time allocation isn't hours — it's which week(s) a task will happen in. Look at how much runway is actually left before each upcoming checkpoint, and size tasks to fit realistically within it.

Upcoming checkpointWhat's expected by then
Preferred design milestoneDesign ideas explored and a preferred design confirmed, with evaluation criteria set.
Development beginsTools and techniques chosen; the build phase starts.
Mid-build check-inGantt chart revisited — task status updated, at-risk dependencies flagged.
Build-complete milestoneProof of concept, prototype, or product substantially finished, ready for testing.

Estimate honestly, not optimistically

It's common to underestimate integration and testing time. If every task on your list is "1 week", that's usually a sign the estimate hasn't accounted for things going wrong — build in a little slack on your riskiest tasks.

Explicit Explanation · D4.2 Dependencies & Sequencing

Some tasks can only start once another task finishes — that's a dependency. Other tasks don't rely on each other at all, and can run in parallel. Spotting the difference is what turns a simple list into an actual schedule.

A familiar example — making breakfast

Toast takes 3 minutes and tea takes 4 minutes to steep — but boiling the kettle doesn't depend on the toaster, so they can run at the same time. Buttering the toast, however, depends on the toast finishing first. The total time isn't the sum of every step — it's determined by the longest chain of steps that do depend on each other.

Dependent (sequential)Independent (parallel)
"Connect the notification feature to the database" can't start until the database schema is built."Design the app's colour scheme" and "research a notification library" can happen at the same time.

Explicit Explanation · D4.2 The Critical Path

The critical path is the longest chain of dependent tasks running from the start of the project to the end. It's called "critical" because a delay anywhere on that chain delays the whole project — a delay on a task that isn't on the critical path usually doesn't, as long as it finishes before whatever depends on it needs it.

Finding your critical path

Trace forward from your first task through every dependency chain to your last task. Add up the durations along each possible chain. The chain with the longest total is your critical path.

6
Explicit Explanation · D4.2 Milestones & Monitoring

A Gantt chart isn't a document you write once and file away — it's revisited at defined points so a group can catch drift early rather than discovering it near a deadline. Your class will formally revisit this Gantt chart at the mid-build check-in and again at the start of Term 4.

What "monitoring" actually looks like

At each check-in, update task status against the plan (done / in progress / not started), and flag anything at risk of missing its date — ideally with a reason and what the group intends to do about it, not just a red flag on its own.

7
Explicit Explanation · D4.2 Task Delegation & Accountability

"The group" is not an owner. Every task on a real project plan needs a named person (or people) responsible for it — otherwise tasks quietly become no one's job until it's too late.

No real accountability

Task: "Build the notification feature." Owner: (blank / "everyone").

Clear accountability

Task: "Build the notification feature." Owner: named group member, with a second member as backup for testing.

This is also the point to be honest about skill gaps — if a task depends on a tool or technique nobody in the group currently knows, that's worth surfacing now, not discovering mid-build.
