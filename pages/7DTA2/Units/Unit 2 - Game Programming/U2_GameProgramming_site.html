Explicit Explanation
The Design Process
Explanation

Making something and designing something aren't the same thing. Making is just doing — picking up materials and producing a result. Designing is doing it with a process: understanding the problem first, planning a response, building it, then checking whether it actually solved the problem. Every project in this unit, including your CAT, follows this process.

The Four Stages

1
Identify
What's the actual problem or brief? What does a successful solution need to do?
2
Plan
Sketch, sequence, or flowchart your approach before you start building.
3
Create
Build the thing — following your plan, but adjusting as you discover problems.
4
Evaluate
Check the result against the brief. What works? What would you change?
Why this matters for code
Most bugs in a program are actually Plan-stage problems showing up during Create. If your algorithm or flowchart was vague, the code built from it will be vague too. Lesson 3 teaches you how to plan precisely, before any building starts.

Explicit Explanation
How Pixels Work
Explanation

Every digital image — a photo, an icon, a game sprite — is built from a grid of pixels, each one a single block of colour. Zoom into any image far enough and you'll see the grid. Pixel art embraces this directly: instead of hiding the grid, it designs with it.

Pixels & Resolution

MakeCode Arcade sprites are typically 16×16 pixels — a small grid. That sounds limiting, but it's exactly what makes pixel art readable at game speed: a player glancing at the screen for a fraction of a second needs to recognise your character instantly.

An 8×8 grid, for illustration — your actual canvas in Piskel will usually be 16×16.

Connection to Data
Each pixel's colour is stored as data — usually as numbers representing red, green and blue values. This is the same "representing data in binary and through media" idea from the Digital Systems strand, just applied directly.

4
Design Principles
Designing Readable Sprites
Principles
  • Work small and bold. Fine detail disappears at 16×16 — strong, simple shapes read better than intricate ones.
  • High contrast. Your player should stand out clearly from your background, even at a glance.
  • Limit your palette. 3–5 colours, reused across all your sprites, makes your game feel like one cohesive world instead of a random collection of images.
  • Silhouette first. If you can recognise the shape with all colours removed, the detail you add on top will only help.
Animation preview
If you're aiming for the Extending criterion, sketch a second frame of your player sprite now — a walk cycle only needs a small change (e.g. legs swapped, or a slight bounce) to read as movement once MakeCode animates between the two frames.

2
Explicit Explanation
What Is an Algorithm?
Explanation
Definition
An algorithm is a precise, ordered sequence of steps to solve a problem or complete a task.

Precise matters as much as ordered. "Make a sandwich" is not an algorithm — it skips every actual step. "Get bread, butter one slice, butter the other, add filling, put slices together" is closer, because someone with no context could follow it.

Worked Example — A Game Event

Here's an algorithm for "player touches an enemy," including a decision:

  1. Player presses A → character jumps
  2. If character lands on enemy → enemy disappears, score + 1
  3. Else → nothing happens
Preview vocabulary
Notice three patterns here: sequence (do this, then this), decision (if... then... else...), and later repetition (do this again and again). You'll build all three directly into MakeCode blocks in Lessons 4 and 5.
3
Explicit Explanation
From Algorithm to Flowchart
Explanation

A flowchart is the same algorithm, drawn as a visual map. Every step gets a shape; arrows show the order; one shape (a diamond) shows a decision splitting into two paths.

SymbolShapeMeaning
Start / EndOvalMarks where the algorithm begins or ends.
ProcessRectangleA single action or step.
DecisionDiamondA yes/no question — splits into two paths.
Flow lineArrowShows the direction and order of steps.

Explicit Explanation
The Event Model
Explanation

Most MakeCode programs are NOT a list of instructions that run top to bottom, like a recipe. Instead, they're built from events — the program waits, and reacts when something happens.

on start
on A button pressed
on sprite of kind Player overlaps sprite of kind Enemy

Each event block holds the instructions that should run when that specific thing happens — and nothing happens until it does.

Connecting back to Lesson 3
The diamond shapes in your flowchart often become event blocks here — a decision point in your algorithm usually corresponds to an "on [event]" block checking a condition.

Explicit Explanation
What Is a Variable?
Explanation
Definition
A variable is a named place to store a value that can change while the program runs.
score
0
→
score
1

Think of a variable as a labelled box. change score by 1 doesn't create a new box — it swaps the number card inside the existing one.

A game without variables can't remember anything. Score, lives, ammo, level, time remaining, whether the door is unlocked — all of it lives in variables.

6
Tool Walkthrough
Score & Lives in MakeCode
Tool
BlockWhat it does
set score to 0Sets the starting value — use this once, on start.
change score by 1Adds to the current value — use this on an event, like a collision.
set life to 3Sets the number of lives, drawn as hearts at the top of the screen.

MakeCode has a built-in score and life system that draws itself on screen. You can also make entirely custom variables from the Variables category for anything else you want to track.

7
Common Pitfalls
What Goes Wrong
Pitfalls
  • Forgetting a starting value. If you never set score to 0, your variable starts undefined — unpredictable behaviour follows.
  • Using set instead of change. set score to 1 always makes score exactly 1, no matter what it was before — it overwrites instead of adding.
  • Putting set score to 0 inside the collision event. Then the score resets every time the player scores, so it never gets past 1.
Test this yourself
In your own project, try swapping change score by 1 for set score to 1 on a repeated collision event, and watch what happens to the displayed score. This is the kind of thing worth breaking on purpose, once, so you recognise it later.

2
Explicit Explanation
Conditionals
Explanation
Definition
A conditional runs one block of code if a condition is true, and (optionally) a different block if it's false.
on sprite of kind Player overlaps otherSprite of kind Enemy if life <= 1 then game over LOSE else change life by -1

Read it as one sentence: when the player touches an enemy, if that was their last life, end the game — otherwise just take a life away. This maps directly onto the decision diamond from Lesson 3 — the diamond's "yes" and "no" exits become the if and else branches here.

If without else
else is optional. if score >= 5 then game over WIN is a complete, valid conditional — when the condition is false, nothing happens and the game carries on.
3
Reference
Comparison Operators
Reference

The condition inside an if is almost always a comparison. These live in the Logic category.

OperatorTrue when…Game example
=The two values are exactly equalif life = 0
≠The two values are not equalif level ≠ 1
<The left value is smallerif score < 5
>The left value is biggerif enemies > 10
<=The left value is smaller, or equalif life <= 1
>=The left value is bigger, or equalif score >= 5
The classic off-by-one bug
< and <= are not interchangeable. if score > 5 needs six points to fire; if score >= 5 fires on the fifth. Choosing the wrong one is the most common logic bug in this unit — and the program will never tell you, because it isn't an error, just the wrong rule.
4
Explicit Explanation
Loops
Explanation
Definition
A loop repeats a block of code, either forever or a set number of times.
LoopWhat it doesUse it for
repeat (4) timesRuns the blocks inside exactly 4 times, then stopsSetting up a starting wave of enemies or coins
foreverRuns the blocks inside over and over until the game endsSpawning enemies, background music, continuous checks
while <condition>Keeps repeating only while the condition stays trueBehaviour that should stop once something changes
forever create enemy sprite pause (1500) ms

This spawns a new enemy every 1.5 seconds, indefinitely.

Every forever loop needs a pause
Remove the pause and the loop runs hundreds of times a second — the game floods with sprites and freezes almost immediately. You will deliberately cause this bug in Step 6 so you recognise it when it happens by accident.
5
Worked Example
A Conditional Inside a Loop
Explanation

Conditionals and loops are far more useful together than apart. A loop asks "do this again"; a conditional inside it asks "…but should I do it the same way this time?"

forever spawn an enemy at a random x position if score >= 3 then pause (700) ms else pause (1500) ms

The loop always spawns. The conditional decides how long to wait before the next one — so the game speeds up once the player reaches 3 points. That is a difficulty ramp, written in five blocks.

What the loop does
Spawn enemy
↓
Check score
↓
Pause (long or short)
↓ back to the top
What the player feels

↓
3 points reached
↓
Late game: pressure builds

Explicit Explanation
Giving Good Feedback
Explanation

Good peer feedback is specific and criteria-based — not generic praise.

Generic (avoid)Specific (aim for)
"It's good.""The controls felt slightly delayed when jumping."
"I like it.""The score feedback made it really clear when I was doing well."

Use the four criteria from Lesson 6 — controls, goal, feedback, difficulty — as your starting point for every comment.

3
Application of Learning
Showcase Format
Activity
  1. Small groups of 3–4 students.
  2. Each student demos their game for ~2 minutes while others play or watch.
  3. Observers note one piece of feedback against the four critique criteria.
  4. Rotate until everyone in the group has presented.
Uncomfortable presenting live?
You can pre-record a short screen capture of your game instead, and play it to your small group rather than presenting in real time. The same critique process applies either way.
